# 验证闭环（G3）

把"写完代码必须验证"固化成可执行的纪律。任何改动，**没有客观证据通过，就不算完成**。

## 何时用
- 完成任意代码/配置改动后（多文件改动尤其必须）
- 用户说「验证」「检查」「跑测试」「确认没问题」
- 准备向用户汇报「做完了」之前

## 步骤
1. **确认验证手段**：读取项目上下文文件（如 AGENTS.md / 项目技术上下文）与 `package.json` / `pyproject.toml` / `Makefile` / `Cargo.toml` 等，确定本项目的：
   - 测试命令
   - lint 命令
   - 类型检查命令
   - 构建命令
2. **跑测试**：执行测试命令，必须 exit 0。
3. **跑 lint**：执行 lint，0 错误（warning 需评估，不得掩盖）。
4. **跑类型检查**（若有）：必须无类型错误。
5. **跑构建**（若适用）：构建必须成功。
6. 全部通过，才标记「完成」。

## 通过标准（pass criteria）
- 测试：exit 0
- lint：0 error（warning 需评估，不得掩盖）
- 类型检查：0 error
- 构建：产物生成且无报错

## 失败响应
- 任一步失败：**读取报错 → 定位根因 → 修复 → 重新跑该步及受影响步骤**，形成闭环。
- 严禁：用「编译过了」「应该没问题」「逻辑看起来对」代替客观验证。
- 循环直到全绿；实在无法在本环境跑（如缺依赖/需 GUI），明确告知用户「未做 X 验证」，不得假装完成。

## 边界
- 项目尚无测试框架：至少跑构建 + 静态检查；并提示主人补最小测试。
- 本项目（playerthree 等）当前为空：此 skill 为未来代码就绪时的合同，改动发生后即生效。
