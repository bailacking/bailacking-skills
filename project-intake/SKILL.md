# 项目信息访谈（project-intake）

## 定位

把模糊 / 空白的项目信息，通过**多轮、由浅入深的访谈**补全成结构化文档。核心不是「我问完就写」，而是**你（大帅）觉得补全了，我才整理**。

## 何时用

- 大帅说「把 \*\*\* 问清楚」「补全项目信息」「访谈我」「帮我梳理这个项目」。
- 某项目目录存在但技术栈 / 目标空白，需要建立上下文（呼应 G1 建档纪律）。

## 核心原则

1. **不问显然的**：不问已答过的，不问能从代码 / 上下文直接看出的。
2. **不接受表面答案**：说「随便 / 都行」时，用选项逼出真实偏好。
3. **不替大帅定需求**：假设显式写出来请确认，绝不臆造核心逻辑（铁律）。
4. **检测知识缺口并教育**：大帅是小白，不确定时给类比 + 选项，不让他做无知决策。
5. **挖掘隐藏假设**：每轮追问「如果 X 不成立怎么办」「X 和 Y 冲突时保哪个」。

## 硬边界（不可动摇）

- **用户喊停才收尾**：每轮访谈后必问「还有要补充的吗？可以整理成文档了吗？」；只有大帅明确说「可以 / 补全了」才生成文档。我不自判「已完整」就动手写。
- **不自动写文件**：文档是访谈产物，未经大帅确认收尾不落盘。
- **不突破建档纪律**：输出默认新建markdown；若项目目录不明，先问落点。

## 提问方式（大帅 v1.1 硬要求，务必遵守）

**总体比例：选择题为主、开放题为辅。** 每轮 2-4 题，其中选择题应占多数；仅在确需要大帅自由发挥处（如「用一句话描述痛点」）才用开放题。

### A. 选择题（默认形态）

用 `AskUserQuestion` 抛出，**每个选项必须**：

1. **`label`** = 简短标签（推荐项在末尾加「（推荐）」）。
2. **`description`** = 1-2 句**选项简介**（这个选项是什么意思、适合什么情况），让小白一看就懂。
3. **推荐项**：把我认为最合适的选项排在第一位，并在其 `description` 里**写明推荐理由**（为什么对当前项目合适）。其余选项也可补一句「若不 X 则选它」。

> 规则：每题 2-4 个选项；始终保留一个「我不确定 / 你帮我定」类选项，别逼小白硬选。

**示例（选择题 + 选项简介 + 推荐项 + 理由）**：

```
AskUserQuestion([
 { question: "playerthree 这个头戴鼠标，软件部分主要给谁用？", header: "用户",
   options: [
     { label: "手部不便人群（推荐）", description: "辅助设备，易用性/无障碍优先；从你'批量生产商用上市'的目标看，这是最可及的刚需市场，建议以此为核心用户" },
     { label: "普通程序员", description: "当作效率/极客工具，功能与可玩性优先；市场较窄但口碑传播快" },
     { label: "只有我自己", description: "先自用验证，暂不考虑他人；最省事但难商业化" },
     { label: "我不确定", description: "我帮你拉竞品资料，一起定用户画像" } ] }
])
```

### B. 开放题（少数，且必须附模板）

仅在需要大帅自由描述处使用（如一句话定位、自由补充）。**必须同时给出「简单回答模板」**，降低小白表达门槛——模板给几个填空词，他照着填即可。

**示例（开放题 + 回答模板）**：

```
文字提问：「用一句话说说，这个项目最想解决的痛点是什么？」
附模板（直接发给他填空）：
  > 现在 ____（谁）做 ____（什么事）时，最麻烦的是 ____（具体痛点），
  > 我希望做个 ____（东西） 帮他把 ____（痛点）解决掉。

例：「现在 手部不便的人 用电脑时，最麻烦的是 没法精准控制光标，
      我希望做个 头戴鼠标 帮他把 操作电脑 这件事变轻松。」
```

**开放题模板写法约定**：模板用 `____` 标填空位，配一句完整示例；不强制他照填，只是降低开口门槛。混在选择题轮次里时，开放题放最后，并允许「跳过」。

## 访谈流程

### Phase 1 · 起步定向（2-3 问，选择题为主）

先 broad 问清轮廓，尽量用选择逼出偏好：

- 这项目是**全新东西**，还是**改进已有的**？（选择题）
- 主要给**谁用**？（选择题，见上示例）
- 你心里它大概长啥样——是**网站 / 桌面软件 / 手机App / 轻量工具/脚本**？（选择题，带推荐项）  
  → 据此判断**项目类型**，后续深挖侧重不同。

### Phase 2 · 分类深挖（按域逐类，每类 2-4 问，选择题为主）

顺序推进，每类：

1. 用 `AskUserQuestion` 抛 2-4 个题（**选择题为主**，必要时 1 道开放题附模板）。
2. 检测不确定 → 给类比 / 选项 + 推荐项，不让他瞎选。
3. 记录已定决策。

**问题域清单（融合两源）**：

- **A 问题与目标**：痛点？现在怎么凑合？成功长啥样？怎么衡量？
- **B 用户体验 / 流程**：用户首次打开看到啥、做啥？核心动作是？（一件必须能做的事）出错咋办？用户技术水平？
- **C 数据**：要存啥？临时还是永久？数据从哪来去哪？谁拥有？有隐私 / 合规吗？
- **D 技术地形**：要跟哪些已有系统协作？技术约束（语言 / 框架 / 平台）？部署环境（云 / 本地 / 边缘）？团队技术力？
- **E 规模与性能**：预期多少用户 / 请求（现在 vs 将来）？能接受的响应时间？流量峰值咋办？读多还是写多？
- **F 集成与依赖**：要对接哪些外部服务 / API？第三方依赖？它们挂了咋办？要鉴权吗？
- **G 安全与权限**：谁能做啥？哪些数据敏感（PII / 财务 / 健康）？合规要求（GDPR / HIPAA / SOC2）？怎么登录？
- **H 部署与运维**：怎么部署、谁部署？要监控 / 告警吗？怎么更新 / 回滚？灾备？
- **I 范围与边界**：明确**不**做啥？MVP vs v2 vs 以后？若砍掉一半范围保啥？
- **J 风险与开放问题**：最糟情况？哪些现在定不了、实现时再决？

> 每个域的第一问优先设计成选择题（带选项简介 + 推荐项 + 理由），只有真正需要长描述时才插开放题并附模板。

### Phase 3 · 研究循环（检测到不确定时）

当大帅说「听说 X 好」或明显不了解某技术：

- 用 `WebSearch` / `WebFetch` 查 X vs 替代方案，用大白话总结权衡。
- 回来用**选择题**呈现结论（A 方案 / B 方案 / 我不确定），推荐项附理由，不替他拍板。

### Phase 4 · 冲突解决

发现矛盾需求（如「既要简单又要功能全」「既要实时又要便宜」）：

- 显式摆出冲突，用**选择题**逼优先级：「保 X 还是保 Y？」（两项各带简介，推荐项附理由）。

### Phase 5 · 收尾确认（用户主导）

- 每轮末问：「还有要补充的吗？可以整理成文档了吗？」（用选择题：「可以整理了（推荐）/ 还要补充」）。
- 大帅说「可以」后：先口头复述理解摘要请确认，再写文档。

## AskUserQuestion 用法（WorkBuddy 格式速查）

- 每轮最多 4 个问题；每题选项 2-4 个。
- 每个选项：`{ "label": "短标签（推荐项加「（推荐）」）", "description": "1-2 句选项简介 + 推荐理由" }`。
- `header` 字段 ≤12 字（如「用户」「技术栈」）。
- **选择题必带「我不确定 / 你帮我定」选项**；**开放题必附 `____` 填空模板 + 一句示例**。
- 推荐项排第一位。

## 文档输出（PROJECT.md 结构）

收尾后生成结构化文档，默认写到项目目录 `PROJECT.md`：

```markdown
# [项目名] 项目档案

## 一句话定位
[给谁、解决啥、为什么]

## 目标用户
[角色、技术水平、使用频率]

## 核心功能
- 必须有（P0）：…
- 应该有（P1）：…
- 可以有（P2）：…

## 技术栈
[语言 / 框架 / 平台 / 部署，已定与待定分开标]

## 范围边界
- 明确不做：…
- 若砍半范围保：…

## 关键约束
[性能 / 合规 / 安全 / 预算]

## 风险与开放问题
[最糟情况、待实现时决议的项]
```
