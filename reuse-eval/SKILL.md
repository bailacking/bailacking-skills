# 开源复用评估（G5）

原则（来自全局记忆，主人 2026-08-14 确立）：**遇需求优先搜 GitHub 开源，自行下载/提取/适配/整合复用，不重复造轮子。** 呼应 SOUL 八荣八耻第 4 条。

## 何时用
- 要实现某个功能/模块，且可能已有现成开源实现
- 用户说「用开源」「找现成」「复用」「有没有库」「GitHub 上看看」
- 我判断「这事儿别人应该做过」

## 流程（检索/评估=分析动作，可直接做；下载/整合=动手，须确认）
1. **明确需求**：写下要解决的问题、目标平台/语言、约束。
2. **检索**：WebSearch + WebFetch（含 GitHub API `api.github.com/repos/...`）。记录候选仓库。
3. **评估候选**，逐项打分：
   - **许可证（红线）**：GPL / AGPL 等传染性协议，若涉及闭源商用须**筛除并提示**；MIT/Apache-2.0/BSD 优先。
   - **活跃度**：最近提交时间、star 数、issue 响应、是否 archived。
   - **适配成本**：语言/依赖是否匹配、文档完整性、是否需要大改。
   - **功能匹配**：是否真解决问题，还是勉强。
4. **出对比表 + 适配方案**：列出 2–3 个候选，标注许可证/活跃度/成本/推荐度。
5. **等用户「确认执行」** 才进行下载/整合（git clone / curl / 提取关键模块 / 改写适配）。
6. 整合后走 verify skill 验证。

## 红线清单（不可逾越）
- 不擅自 `git clone` 或下载到项目并整合——必须先给候选+方案，用户说「确认执行」。
- GPL/AGPL 传染性协议：闭源商用场景直接排除并说明。
- 不引入未知来源、无许可证或明显废弃的仓库到生产代码。
